Will Bun Become the New Shell?

Anthropic acquired Bun three weeks after publishing a blog post about replacing MCP tool calls with TypeScript execution. Here's why that matters for how agents work.

Kasper Peulen · April 2026 
# Bash
grep -c "ERROR" server.log

# Bun
bun -e 'console.log((await Bun.file("server.log").text()).split("\n").filter(l => l.includes("ERROR")).length)'

The starting pointUsing Bun to orchestrate MCP

On November 4, 2025, Anthropic published "Code execution with MCP". The idea: instead of agents calling MCP tools one by one — each tool definition consuming context, each intermediate result flowing through the model — let the agent write TypeScript that orchestrates the calls directly in a runtime.

A workflow that consumed 150,000 tokens was reimplemented this way. New cost: 2,000 tokens. Every example was TypeScript.

Three weeks later, Anthropic acquired Bun.

In January 2026, Claude Code shipped MCP Tool Search — deferred loading that pulls tool definitions into context only when needed. This reduced schema overhead by 85%. Simon Willison reversed his stance on MCP: "This is great — now that it's solved there's no reason not to hook up dozens or even hundreds of MCPs."

But deferred loading solves one half. It addresses tool definitions bloating context. The other half — intermediate results flowing through the model when chaining calls — is untouched. Grab a 50,000-token meeting transcript from Google Drive and attach it to Salesforce, and that data passes through the model twice, even with deferred loading.

The blog post's code execution pattern solves this second half. The agent writes a script. The script handles the data. Only the final result hits context.

Cloudflare has already shipped this pattern. Their "Code Mode" exposes the entire Cloudflare API — 2,500+ endpoints — through just two MCP tools: search() and execute(). The agent writes TypeScript against a typed API. Context cost: ~1,000 tokens. A traditional MCP server for the same API: over 2 million.

"We found agents are able to handle many more tools, and more complex tools, when those tools are presented as a TypeScript API rather than directly." — Cloudflare, "Code Mode", September 2025

Going furtherCould Bun replace bash for agents?

"Agents are good at bash. Bash is not good for agents. We should cut our losses and restart now before it is too late." — Theo Browne (t3.gg), April 2026

The code execution pattern doesn't just apply to MCP orchestration. It raises a broader question: if agents are going to write TypeScript to call tools, why not write TypeScript for everything they currently use bash for?

There are two reasons this could make sense.

1. Output filtering. The same problem that plagues MCP tool chaining also plagues bash. When an agent runs a shell command that returns 10,000 lines, all of it flows into context. Yes, the agent can pipe through grep, awk, head, tail, or jq to try to find the right piece — but those operate on unstructured text or loosely-typed JSON. With TypeScript, the agent works with typed objects: .filter(), .map(), and .reduce() on real data structures in the runtime, and only console.log() what the model actually needs to see.

import { drive } from "@anthropic/google";

// 10,000 rows fetched — none hit context
const rows = await drive.getSheet("abc123");
const overdue = rows.filter(r => r.status === "overdue");

// Shell out for what shell is good at
await Bun.$`git add . && git commit -m ${msg}`;

// Only this returns to the model
console.log(`${overdue.length} overdue items`);

2. Safe execution. The Claude Code source leak showed how difficult it is to sandbox bash: two different command parsers running in parallel — one deprecated but still making security decisions — a dangerouslyDisableSandbox escape hatch, and a compaction routine reportedly wasting significant API calls. TypeScript in a controlled runtime sidesteps this. Cloudflare's Code Mode runs generated code in sandboxed Dynamic Workers where outbound fetch() is blocked by default. The runtime enforces boundaries, not command parsers.

What Bun already isA scripting runtime with fast primitives

Bun is interesting here not because it's faster than Node — though it is — but because it's designed as a scripting-first runtime. Some specifics:

Bun.$ provides a built-in cross-platform shell with automatic escaping. But shelling out has overhead. For performance-critical operations, Bun ships fast native primitives — glob, file I/O, hashing — that avoid spawning processes entirely. Startup is ~5ms. And once running, chaining multiple operations through native APIs is significantly faster than sequential shell commands.

// An agent gathering project stats — no processes spawned
import { Glob } from "bun";

const glob = new Glob("src/**/*.ts");
const files = [];

for await (const path of glob.scan({ cwd: "." })) {
  const f = Bun.file(path);
  files.push({ path, size: f.size });
}

const total = files.reduce((s, f) => s + f.size, 0);
const largest = files.sort((a, b) => b.size - a.size).slice(0, 5);

// Only this reaches the model
console.log(`${files.length} files, ${(total / 1024).toFixed(0)}KB total`);
console.log(`Largest:`, largest.map(f => f.path));

Auto-install. The agent can import any package without an npm install step. No package.json required. Bun resolves, caches, runs. The script is self-contained.

# -i auto-installs lodash on first run, caches it after
bun -i -e 'import _ from "lodash"; console.log(_.chunk([1,2,3,4,5,6], 2))'

Native TypeScript. Run .ts directly. No config, no build step.

And Anthropic now controls Bun's direction. Jarred Sumner described the post-acquisition mission as making Bun "the best place to build, run, and test AI-driven software." That control matters for two reasons beyond features.

Performance as infrastructure. When a runtime sits between every agent action and every external service, milliseconds compound. An agent orchestrating a dozen API calls, filtering results, and writing files isn't running one script — it's running hundreds per session. Bun's ~5ms startup and native-speed primitives aren't nice-to-haves at that scale. They're the difference between an agent that feels responsive and one that doesn't. Anthropic can now optimize the runtime specifically for this workload.

Sandboxing by design. The safe execution argument cuts deeper when you own the runtime. Anthropic doesn't need to bolt sandboxing onto an existing shell — they can build it into Bun itself. Imagine a --sandbox flag that restricts filesystem access, blocks outbound network by default, and enforces capability-based permissions at the runtime level. Not a wrapper around bash. Not a container. A runtime that is the sandbox. Cloudflare proved this works with Dynamic Workers. Anthropic can now do the same thing locally.

The shape of thingsDo agents even need MCP?

If the agent writes TypeScript and Bun runs it, the interface to external services doesn't need to be a protocol at all. It could just be packages.

import { drive } from "@anthropic/google";
import { channels } from "@anthropic/slack";

const doc = await drive.getDocument("abc123");
await channels.post("general", doc.summary);

Or a more complex workflow — cross-referencing services, filtering locally, reporting only the result:

import { calendar } from "@anthropic/google";
import { issues } from "@anthropic/linear";
import { channels } from "@anthropic/slack";

// Fetch from three services in parallel
const [meetings, tickets] = await Promise.all([
  calendar.getEvents({ date: "today" }),
  issues.list({ assignee: "me", state: "active" }),
]);

// Cross-reference locally — zero tokens spent
const atRisk = tickets.filter(t =>
  t.dueDate === "today" &&
  meetings.some(m => m.duration > 60)
);

if (atRisk.length) {
  const summary = atRisk.map(t => `• ${t.title}`).join("\n");
  await channels.post("standup", `⚠️ ${atRisk.length} tickets due today, blocked by long meetings:\n${summary}`);
}

// Model sees: "Posted 2 at-risk tickets to #standup"
console.log(`Posted ${atRisk.length} at-risk tickets to #standup`);

Three services, parallel fetching, local filtering, conditional action — all in one script. The model sees one line of output. No tool schemas were loaded. No MCP server was running.

With auto-install, no setup step. Maybe MCP survives as invisible plumbing underneath — the way HTTP is invisible when you use an SDK. The 97 million monthly SDK downloads and adoption by OpenAI, Google, Microsoft, and AWS suggest momentum. But maybe it doesn't survive at all. If the agent can import a typed package and call APIs directly, what is MCP adding? A protocol is useful when you need a standard interface between arbitrary parties. An agent that writes code doesn't need a standard interface — it needs types, documentation, and a safe execution layer.

ContextWhat others have observed

"Anthropic bought Bun because they want to control the place where AI-written code actually runs." — Nibzard, December 2025
"Models require a 'controllable execution substrate' rather than a traditional operating system. No mainstream large model vendor has ever directly acquired a mature general-purpose language runtime before." — Jimmy Song, December 2025

MCP, CLI, bash — these are all interfaces designed for a world where the caller can't write code. Protocols exist so that dumb clients can talk to smart servers. Command-line tools exist so that humans can type instructions. But an agent that generates TypeScript doesn't need any of that. Google, Slack, Linear, Stripe — they all ship TypeScript SDKs already, many with millions of weekly downloads. MCP wraps those SDKs in a protocol so that tool-calling agents can use them. An agent that writes code can just use the SDKs directly. The protocol becomes a redundant abstraction.

That's what makes the Bun acquisition legible. Anthropic didn't buy a JavaScript bundler. They bought the execution layer.

The open questionSo will Bun become the new bash?

The pieces are in place. Anthropic owns the runtime. The code execution pattern is proven. Deferred loading handles tool definitions; code execution handles intermediate results. The question is whether this stays a power-user pattern or becomes the default.

That depends on training. Today's models are steeped in bash — decades of Stack Overflow answers, man pages, and dotfiles in the training data. If Anthropic starts training models to reach for Bun.$ before /bin/sh, to .filter() before grep, the shift could happen fast. They own the runtime and the model — that's a tight feedback loop.

Meanwhile, I've already switched. I've set up my agent to run everything through bun -e. No more bash. So far, it works great. Excited to see how this will unfold!
