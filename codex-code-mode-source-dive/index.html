V8 isolates are the new shell in Codex Code Mode

I cloned the OpenAI Codex repo and read the Code Mode internals. Codex makes JavaScript the agent shell with in-process V8 isolates — not Bun, not subprocesses.

The hidden switchTwo flags, two tools

Codex 0.134.0 ships two off-by-default feature flags: code_mode and code_mode_only. Turning on code_mode_only also turns on code_mode. With them set, the model's tool surface collapses to two entries: exec and wait.

exec is a freeform tool. The model sends raw JavaScript source text — not JSON, not a fenced block. Codex strips an optional // @exec: pragma, allocates a cell id, spins up a fresh V8 isolate, and evaluates the source as an async module. The call returns either the completed output or a Script running with cell ID ... header if execution exceeds the 10-second yield window.

wait is the companion. It takes a cell_id and resumes a still-running isolate, returning only output emitted since the previous yield. Pass terminate: true to kill the cell. The tests confirm multiple cells can be alive at once and a terminated cell leaves later exec calls unaffected.

The runtimeA V8 cell between the model and tools

The implementation splits across three locations. codex-rs/code-mode owns the V8 runtime: globals, cell lifecycle, waits, timers, image and text buffering, the session store. codex-rs/core/src/tools/code_mode wires that runtime into the Codex tool system. codex-rs/tools/src/code_mode.rs converts ordinary tool specs into nested JavaScript functions and renders their JSON Schemas as TypeScript declarations.

The isolate is minimal by construction. The runtime deletes console, Atomics, SharedArrayBuffer, and WebAssembly. import is unsupported. There is no Node API, no filesystem handle, no fetch. To do anything outside the isolate the script must call a function on tools, which round-trips back through Codex's tool runtime as a real tool call.

Output to the model goes through three globals. text(value) appends an input_text item to the cell's buffer; on yield or completion, Codex wraps the buffer as a single custom_tool_call_output. image(item) appends an image — from an HTTPS URL, a data URL, an object with image_url, or a raw MCP image block. notify(value) flushes a custom_tool_call_output immediately while the cell keeps running, so the model can react before the script finishes. Everything else — intermediate awaits, parsed JSON, half-built arrays — stays inside V8 and dies with the cell.

// Two shell calls in parallel; only the summary leaves the cell.
const [diff, tests] = await Promise.all([
  tools.exec_command({ cmd: "git diff --stat", max_output_tokens: 4000 }),
  tools.exec_command({
    cmd: "pnpm test -- --reporter=json",
    max_output_tokens: 40000,
  }),
]);

let failures = [];
try {
  failures = JSON.parse(tests.output).testResults
    .flatMap((file) => file.assertionResults ?? [])
    .filter((t) => t.status === "failed")
    .map((t) => t.fullName)
    .slice(0, 10);
} catch {}

text(JSON.stringify({
  changed: diff.output.trim(),
  failed_tests: failures,
  exit_code: tests.exit_code,
}, null, 2));
GlobalWhat it does
toolsObject of async functions, one per enabled nested Codex tool. Each call emits a runtime tool-call event; the turn worker runs the real tool and resolves the Promise with parsed JSON.
ALL_TOOLSCatalog of enabled nested tools as { name, description }. Descriptions carry the same generated TypeScript declarations the model sees up front. Useful for deferred-tool catalogs.
textAppends an input_text output content item to the cell buffer. The buffer becomes one custom_tool_call_output when exec or wait responds.
imageAppends an image output item. Accepts HTTPS URLs, data URLs, { image_url } objects, and raw MCP image blocks.
store / loadRead and write JSON-serializable values under string keys, scoped to the session. A later exec cell can load what an earlier one stored.
notifyFlushes a separate custom_tool_call_output immediately, before the cell finishes. Skips the buffer.
yield_controlHands the buffered output back to the model now. The cell keeps running; subsequent wait calls receive new output.
exitStops the script successfully, like an early top-level return.

TypeScript in the promptJavaScript in V8

Code Mode uses TypeScript syntax as tool documentation, not as the execution language. For each enabled nested tool, codex-rs/tools/src/code_mode.rs renders its JSON Schema into a declare const tools block and appends it to the exec description. The model reads those declarations before it writes a cell, so it knows which tools.* functions exist and what arguments they take.

// Generated into the exec description from the MCP server's JSON Schema.
declare const tools: {
  mcp__rmcp__echo(args: { env_var?: string; message: string; }):
    Promise<CallToolResult<{ echo: string; env: string | null; }>>;
};

// The cell itself is plain JavaScript; the declaration block is prompt text.
const result = await tools.mcp__rmcp__echo({ message: "ping" });
text(result.structuredContent?.echo ?? "missing");

At execution time, none of that TypeScript reaches V8. execute_handler.rs hands the raw source — minus the optional pragma — to compile_module. Type annotations, declare blocks, and other TypeScript-only syntax are invalid there. Argument validation happens later, when JavaScript calls a nested tool and the JSON payload goes through Codex's normal tool runtime.

The benchmarkA warm cell is under a millisecond

One local measurement on an Apple M1 Pro running Darwin 24.6.0, Bun 1.3.11, Codex at commit a75c443. Code Mode cells were driven through CodeModeService::execute in a release build; Bun was launched as a subprocess with stdio discarded. The warm paths ran for 1,000 iterations.

A warm Code Mode cell creates an isolate, installs the global surface, evaluates a module, and tears down in under a millisecond on this machine. Bun is a full runtime launched as a subprocess. Codex made JavaScript orchestration cheap enough to sit inside the agent loop without a process spawn per cell.

What the tests pin downConcrete behavior

The behavior the project intends to preserve lives in codex-rs/core/tests/suite/code_mode.rs.

Nested tools are async functions. Even when only exec and wait are visible to the model, registered tools remain callable from JavaScript.

// code_mode_only_can_call_nested_tools
const output = await tools.exec_command({
  cmd: "printf code_mode_only_nested_tool_marker",
});
text(output.output);

Nested calls run in parallel. A barrier-and-delay pair proves the two tool calls are not serialized.

// code_mode_nested_tool_calls_can_run_in_parallel
const args = {
  sleep_after_ms: 300,
  barrier: { id: "code-mode-parallel-tools", participants: 2, timeout_ms: 1000 },
};

const results = await Promise.all([
  tools.test_sync_tool(args),
  tools.test_sync_tool(args),
]);

text(JSON.stringify(results));

Long-running cells yield and resume. exec returns "phase 1" and a cell id; a later wait receives only "phase 2" and "phase 3" with Script completed.

// code_mode_can_yield_and_resume_with_wait
text("phase 1");
yield_control();
text("phase 2");
text("phase 3");
# The wait call from the model is a normal function tool, not JavaScript.
wait {
  "cell_id": "1",
  "yield_time_ms": 1000
}

State crosses turns. store and load persist JSON values across exec calls in the same session.

// Turn N: save a small JSON value under "nb".
store("nb", { title: "Notebook", items: [1, true, null] });
text("stored");

// Turn N+1: load and return it.
text(JSON.stringify(load("nb")));

Deferred tools stay callable. Codex can omit some deferred app or MCP tools from the printed exec description while keeping them callable and listed in ALL_TOOLS.

MCPOne Codex tool per MCP tool

Each MCP tool exposed to Codex becomes a function on tools. A namespaced MCP tool such as rmcp.echo becomes tools.mcp__rmcp__echo; characters that are invalid in JavaScript identifiers are normalized to underscores, while the raw server and tool names go out over the wire. The Promise resolves to the MCP CallToolResult directly: content, structuredContent, and isError are inspectable JavaScript objects.

The cell inspects content, structuredContent, and isError before deciding what reaches the model. The same set of tests covers text-only results, structured results, image forwarding through image(), error summaries, and code_mode_only reaching MCP tools that were never surfaced at the top level.

The shapeWhere this fits the Bun argument

The Bun post argued that JavaScript would become the agent shell: agent writes a script, runtime holds the intermediate results, only the selected output goes back to the model. Codex implements that with in-process V8 isolates and a Rust harness. No subprocess per cell, no Node, no npm install step, no shared filesystem — just a small, sandboxed JS surface that calls Codex's existing tools.

The Bun argument turned on owning the runtime. Codex shows another route: own the harness, embed V8 directly, and the agent loop never has to spawn a process to run JavaScript.
