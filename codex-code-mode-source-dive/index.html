Codex Code Mode is not a shell

I cloned the OpenAI Codex repo, inspected the hidden Code Mode internals, and found a small V8 runtime that lets agents compose tools with JavaScript.

The starting pointA hidden switch in the harness

After writing about Bun becoming an agent shell, I wanted to know whether OpenAI was moving in the same direction. The answer is sitting in the open-source Codex harness.

The feature registry contains two under-development flags: code_mode and code_mode_only. On my installed codex-cli 0.134.0, both are off by default. Enabling code_mode_only automatically enables code_mode too.

Code Mode is not a second shell. It is a tiny JavaScript coordination layer between the model and Codex tools. — My read of codex-rs/code-mode

The public tool names are deliberately boring: exec and wait. But exec does not run bash. It accepts raw JavaScript, evaluates it as an async module inside V8, and injects a tools object that can call back into Codex's normal tool runtime.

The machineryA V8 cell between the model and tools

The implementation is split across three places. codex-rs/code-mode owns the V8 runtime, globals, cells, waits, and stored values. codex-rs/core/src/tools/code_mode adapts that runtime into Codex's tool system. codex-rs/tools/src/code_mode.rs converts ordinary tool specs into nested JavaScript functions.

Model sees exec and writes JavaScript
calls
V8 runtime exposes tools, ALL_TOOLS, text, store, load
proxies
Codex runs the real shell, MCP, browser, app, or workspace tool

The sandbox is small on purpose. The runtime deletes console, Atomics, SharedArrayBuffer, and WebAssembly. Module imports are unsupported. There is no Node, no direct filesystem, and no direct network. If the script wants power, it has to ask a Codex tool for it.

// A representative Code Mode cell, not copied from the repo.
const [status, tests] = await Promise.all([
  tools.exec_command({ cmd: "git status --short" }),
  tools.exec_command({ cmd: "pnpm test", max_output_tokens: 1200 }),
]);

store("last_status", status.output);

text({
  dirty: status.output.trim().length > 0,
  test_exit_code: tests.exit_code,
});

This is the important shift: the model can run a little program that does branching, filtering, parallel calls, and state updates before sending a tiny result back into context.

The agent patternWhy this matters for tool use

Traditional tool calling makes the model the orchestration layer. Call a tool, read the result, decide, call another tool, read the result again. That is easy to debug, but expensive. Every intermediate result travels through the model context.

Code Mode moves orchestration into a disposable script. The model still chooses the plan, but JavaScript handles the boring parts: parallelism, filtering, joining data, counting rows, trimming logs, and returning only the conclusion.

// Discover tools even when they were deferred from the visible prompt.
const matches = ALL_TOOLS
  .filter(({ name, description }) =>
    /storybook|chromatic|mcp|docs/i.test(`${name} ${description}`)
  )
  .map(({ name }) => name);

text(JSON.stringify(matches, null, 2));

The quiet power here is ALL_TOOLS. The repo tests cover deferred app tools that are omitted from the top-level model prompt but remain discoverable and callable from Code Mode. That means code_mode_only is prompt shaping, not a capability firewall.

If an agent has to use dozens of tools, the scalable interface may not be a bigger prompt. It may be a small program.

MCPHow Code Mode connects to MCP

There are two versions of the pattern now. In the Codex repo, Code Mode is client-side: Codex creates the JavaScript runtime, and any MCP tools already registered with Codex become callable nested functions. The generated function names are JavaScript-safe names such as mcp__server_name__tool_name, while the raw MCP server and tool names are preserved underneath.

Cloudflare and Anthropic describe the server-side version. Instead of exposing hundreds or thousands of MCP tools directly, the MCP server exposes a tiny code execution surface. The agent writes TypeScript against a typed API, and the server executes it inside a sandbox. Cloudflare says this lets agents handle much larger APIs with a fixed prompt footprint.

This is exactly the same direction as the Bun post. Agents are good at writing code. The more tool catalogs grow, the more tempting it becomes to give the agent a real programming surface and let it reduce the mess locally.

Repo secretsWhat surprised me

First: exec is a freeform tool. The grammar accepts raw JavaScript, with an optional first-line // @exec: pragma for yield and output budgets. That is very different from a normal JSON-schema tool call.

Second: cells can yield and be resumed. The runtime has yield_control(), a wait tool, default yield windows, termination handling, and stored values. This is not just eval. It is a little session runtime.

Third: latest main is hardening behavior, not just sketching it. Comparing rust-v0.134.0 with the inspected main commit touched Code Mode paths across 14 files, with new or expanded tests for parallel nested calls, ALL_TOOLS, MCP result shapes, images, hidden tools, store/load, and wait behavior.

Fourth: Code Mode Only does not mean "only two capabilities." It means "only two top-level tools in the prompt." The JavaScript runtime can still call nested tools that Codex registered for Code Mode.

The cautionThis is not a stable user feature yet

The repo marks both flags as UnderDevelopment. OpenAI's feature maturity docs say under-development features are not ready for use. So the right posture is curiosity, not dependency.

# Local lab only
codex --enable code_mode
codex --enable code_mode_only

# Evidence on this machine
codex features list | rg '^code_mode'

The safest experiment is read-only: ask Codex to inspect ALL_TOOLS, call harmless local commands, and return tiny summaries. I would not build durable workflows on this until OpenAI promotes the feature to experimental or stable in public docs.

The bigger pictureClients will catch up

The source dive made the public trend clearer. Anthropic is talking about code execution around MCP. Cloudflare shipped Code Mode for enormous APIs. FastMCP can wrap existing MCP servers in a Code Mode transform. OpenAI's open-source harness has a V8-based version hiding behind flags.

The direction is not "agents need more buttons." It is "agents need a safe place to write small programs." Bash is one answer. Bun is another. Codex Code Mode is a constrained version where the runtime cannot touch the world directly, but can ask approved tools to do it.

The future agent client may look less like a tool picker and more like a notebook kernel with permissions. — That is the bet I see in the repo
