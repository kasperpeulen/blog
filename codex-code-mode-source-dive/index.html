V8 isolates are the new shell in Codex Code Mode

I cloned the OpenAI Codex repo, inspected the hidden Code Mode internals, and found that Codex is using V8 isolates, not Bun, to make JavaScript the agent shell.

Kasper Peulen · May 2026

    .slice(0, 5),

The starting pointA hidden switch in the harness

After writing about Bun becoming an agent shell, I wanted to know whether OpenAI was moving in the same direction. The answer is yes, but not with Bun. The open-source Codex harness has its own JavaScript execution path built on in-process V8 isolates.

The feature registry contains two under-development flags: code_mode and code_mode_only. On my installed codex-cli 0.134.0, both are off by default. Enabling code_mode_only automatically enables code_mode too.

The idea is the same as the Bun post: JavaScript is becoming the new shell for agents. Codex just reaches for V8 isolates instead of Bun. — My read of codex-rs/code-mode

The public tool names are deliberately boring: exec and wait. They are not boring internally. exec is a freeform tool: the model sends raw JavaScript source text, not JSON and not a markdown code fence. Codex parses an optional first-line pragma, allocates a cell id, starts a fresh V8 isolate, evaluates the source as an async module, and returns either a completed result or a "Script running with cell ID ..." header.

wait is the companion function tool. It takes a cell_id, waits for new output from that already-running isolate, optionally truncates the returned output with max_tokens, and can terminate the cell with terminate: true. The tests prove that one turn can start a cell, later turns can wait on it, multiple cells can be alive at once, and termination does not poison later exec calls.

The machineryA V8 cell between the model and tools

The implementation is split across three places. codex-rs/code-mode owns the V8 runtime, globals, cells, waits, timers, image/text helpers, and stored values. codex-rs/core/src/tools/code_mode adapts that runtime into Codex's tool system. codex-rs/tools/src/code_mode.rs converts ordinary tool specs into nested JavaScript functions and appends TypeScript declarations to their descriptions.

The sandbox is small on purpose. The runtime deletes console, Atomics, SharedArrayBuffer, and WebAssembly. Module imports are unsupported. There is no Node, no direct filesystem, and no direct network. If the script wants power, it has to ask a Codex tool for it. I did not find a startup benchmark in the repo, so I would not claim V8 is faster than Bun here. The architectural fact is narrower and stronger: this is in-process isolate startup, not a spawned shell process.

The important practical detail is the return channel. A Code Mode script can call tools, branch, filter, and keep intermediate results private inside V8. The model does not automatically see all of that. The model sees what the script gives back through text() or image() when exec or wait yields or completes. In other words, text() is closer to "return this to the agent" than "print this to the user."

// Awaiting tools gives the output to JavaScript, not directly to the model.
const [diff, tests] = await Promise.all([
  tools.exec_command({ cmd: "git diff --stat", max_output_tokens: 4000 }),
  tools.exec_command({
    cmd: "pnpm test -- --reporter=json",
    max_output_tokens: 40000,
  }),
]);

// The script can parse, filter, and summarize a noisy test payload locally.
let failures = [];
try {
  failures = JSON.parse(tests.output).testResults
    .flatMap((file) => file.assertionResults ?? [])
    .filter((test) => test.status === "failed")
    .map((test) => test.fullName)
    .slice(0, 10);
} catch {}

// text(...) is the return channel back to the agent/model.
text(JSON.stringify({
  changed: diff.output.trim(),
  failed_tests: failures,
  exit_code: tests.exit_code,
}, null, 2));

The TypeScript sideDeclarations, not tsc

There are two different layers here. The prompt surface can be TypeScript-shaped: in code_mode_only, Codex renders known nested tool schemas as TypeScript declarations in the exec description so the model knows how to call tools.*. The runtime surface is JavaScript-only: exec accepts raw JavaScript, strips only the optional // @exec: pragma, and sends the remaining source to V8 as a module.

// Generated into the exec description before the model writes JS.
declare const tools: {
  mcp__rmcp__echo(args: { env_var?: string; message: string; }):
    Promise<CallToolResult<{ echo: string; env: string | null; }>>;
};

// The agent then writes ordinary JavaScript for V8 to run.
const result = await tools.mcp__rmcp__echo({ message: "ping" });
text(result.structuredContent?.echo ?? "missing");

I did not find a TypeScript compiler, transpiler, or tsc validation step in the Code Mode execution path. That matters. The generated declare const tools block is a prompt/type hint, not code that runs. If the model sends TypeScript-only syntax to exec, V8 sees it as JavaScript source and the cell fails at runtime. Tool argument errors are runtime tool errors, not static type errors.

Agent examplesThe old Bun scripts in Codex clothes

The old Bun post had more interesting examples because it showed whole workflows: calendar, Slack, Linear, sheets, local filtering, one-line output. Code Mode wants the same shape, with one important difference. Bun can import SDKs. Codex's V8 cell cannot import anything. It composes the tools Codex already approved and described to the model.

So the normal path is not "search ALL_TOOLS and hope." The model should already have generated declarations for known tools before it writes JavaScript. The examples below use connector-style names from the current tool catalog, normalized into JavaScript identifiers.

// Meeting prep: Calendar, Linear, Slack, Notion; one tiny return value.
const [calendar, tickets, slack, notes] = await Promise.all([
  tools.google_calendar_search_events({
    query: "Code Mode",
    time_min: "2026-05-27T00:00:00Z",
    time_max: "2026-05-28T00:00:00Z",
    max_results: 10,
  }),
  tools.linear_list_issues({
    assignee: "me",
    state: "active",
    priority: 2,
    limit: 50,
    orderBy: "updatedAt",
  }),
  tools.slack_slack_search_public_and_private({
    query: '"Code Mode" "MCP" after:2026-05-01',
    limit: 20,
    include_context: false,
  }),
  tools.notion_search({
    query: "Code Mode MCP launch notes",
    query_type: "internal",
    page_size: 5,
    filters: {},
  }),
]);

// All the noisy result shapes stay inside the V8 cell.
const meetings = (calendar.items ?? calendar.events ?? [])
  .map((event) => event.summary ?? event.title)
  .filter(Boolean);

const highPriority = (tickets.issues ?? tickets.nodes ?? tickets.results ?? [])
  .map((issue) => issue.identifier ?? issue.title)
  .filter(Boolean)
  .slice(0, 10);

const threads = (slack.results ?? slack.matches ?? [])
  .map((hit) => hit.permalink ?? hit.url ?? hit.text)
  .filter(Boolean)
  .slice(0, 5);

const docs = (notes.results ?? [])
  .map((page) => page.title ?? page.url)
  .filter(Boolean);

// The model gets the brief, not every calendar event and Slack hit.
text(JSON.stringify({
  meetings,
  high_priority_tickets: highPriority,
  threads,
  docs,
}, null, 2));

That is basically the old Calendar + Linear + Slack + notes example, but with Codex's security boundary preserved. The JavaScript has no direct network. It can only ask approved tools to do work, then reduce the returned objects before calling text().

Actual testsThe repo patterns are concrete

The examples above are the practical shape. The proof is lower-level and lives in codex-rs/core/tests/suite/code_mode.rs. Those tests show what Code Mode actually guarantees.

1. Nested tools are normal async functions. Even in code_mode_only, where the top-level model prompt only lists exec and wait, JavaScript can still call registered nested tools.

// From code_mode_only_can_call_nested_tools
// Call an ordinary Codex tool from inside the V8 cell.
const output = await tools.exec_command({
  cmd: "printf code_mode_only_nested_tool_marker"
});

// Return only the useful command output to the agent.
text(output.output);

That is the shell replacement shape in miniature. The agent writes JavaScript; the shell command is demoted to one tool call inside the script.

2. Nested tool calls can run in parallel. The test uses a barrier and two delayed tools, then asserts the total wall time is short enough to prove they were not serialized.

// From code_mode_nested_tool_calls_can_run_in_parallel
const args = {
  sleep_after_ms: 300,
  barrier: {
    id: "code-mode-parallel-tools",
    participants: 2,
    timeout_ms: 1000,
  },
};

// Start both nested tool calls at the same time.
const results = await Promise.all([
  tools.test_sync_tool(args),
  tools.test_sync_tool(args),
]);

// Send the combined result back as one exec output.
text(JSON.stringify(results));

3. Long-running cells yield and resume. exec can return before the JavaScript finishes. The model gets a cell id, then calls wait later. The test verifies that the first response includes "phase 1", the second wait returns only "phase 2", and the final wait returns "phase 3" with Script completed.

// From code_mode_can_yield_and_resume_with_wait
// Emit phase 1 as tool output now.
text("phase 1");

// Return control to the model while the JS cell stays alive.
yield_control();

// Later wait calls receive only output emitted after the yield.
text("phase 2");
text("phase 3");
# The model-facing wait call is JSON, not JavaScript
wait {
  "cell_id": "1",
  "yield_time_ms": 1000
}

4. Small state can cross turns. This is not a durable database. It is session-local JSON state. But it is enough for an agent to save a small object from one exec cell and reuse it in a later one.

// First exec call: keep JSON state inside Code Mode's session store.
store("nb", { title: "Notebook", items: [1, true, null] });

// Return a tiny acknowledgement to the model.
text("stored");

// Later exec call: load the state and explicitly return it.
text(JSON.stringify(load("nb")));

5. Deferred tools are an edge case, not the main workflow. Codex can omit some deferred app or MCP tools from the printed exec description while keeping them callable and listed in ALL_TOOLS. That proves the runtime can handle dynamic catalogs. It does not mean normal agent code should discover every tool by string search at execution time.

MCPHow Code Mode connects to MCP

In the Codex repo, MCP is not a hypothetical wrapper example. The tests register an RMCP server and prove that its tools appear directly on tools. A namespaced MCP tool such as rmcp.echo becomes tools.mcp__rmcp__echo. If the raw tool name contains illegal JavaScript identifier characters, Codex normalizes them to underscores. Underneath, the raw server and tool names are preserved for the actual MCP call.

Cloudflare and Anthropic describe the server-side version. Instead of exposing hundreds or thousands of MCP tools directly, the MCP server exposes a tiny code execution surface. The agent writes TypeScript against a typed API, and the server executes it inside a sandbox. Cloudflare says this lets agents handle much larger APIs with a fixed prompt footprint.

// Call the real MCP tool as a nested JavaScript function.
const { content, structuredContent, isError } =
  await tools.mcp__rmcp__echo({ message: "ping" });

// Reduce the MCP result into a tiny model-visible summary.
text(
  `echo=${structuredContent?.echo ?? "missing"}\n` +
    `isError=${String(isError)}\n` +
    `contentLength=${content.length}`
);
// From code_mode_can_use_mcp_image_result_with_image_helper
// MCP image blocks can be forwarded as image output to the agent.
const out = await tools.mcp__rmcp__image_scenario({
  scenario: "image_only_original_detail",
});

const imageItem = out.content.find((item) => item.type === "image");
image(imageItem);
// From code_mode_can_print_error_mcp_tool_result_fields
// Tool errors are data the JS cell can inspect before summarizing.
const bad = await tools.mcp__rmcp__echo({});
const firstText = bad.content[0]?.text ?? "";

text(JSON.stringify({
  is_error: bad.isError,
  content_items: bad.content.length,
  missing_message:
    firstText.includes("missing field") &&
    firstText.includes("message"),
}, null, 2));

The important bit is the result shape. Code Mode can inspect MCP content, structuredContent, and isError fields in JavaScript before returning anything to the model. Separate tests cover text-only MCP results, structured MCP results, MCP image blocks passed through image(), error results summarized into booleans, and code_mode_only calling MCP tools even when only exec and wait were visible at the top level.
